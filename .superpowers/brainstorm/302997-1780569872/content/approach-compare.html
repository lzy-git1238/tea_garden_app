A vs B：MQTT 双向通信方案对比

核心差异：外部进程 vs Qt 原生库

A: 双进程 mosquitto
mosquitto_pub -l
属性上报 (已有，不动)
mosquitto_sub -F '%j' -t ...
命令监听 (新增)
stdout 逐行 JSON → Qt QProcess 解析
响应怎么办？
需第三个 mosquitto_pub (一次性)
收到命令后起一个临时进程发响应
B: Qt MQTT 模块
QMqttClient
一个长连接，同时 pub + sub
subscribe → messageReceived 信号
publish() → 直接发响应
自动重连、TLS、QoS 内建

✅ A 的优点

  • 不改现有代码架构，IotUploader 保持 mosquitto_pub 模式
  • mosquitto 是系统级工具，TLS 成熟，调试可单独命令行测试
  • 不引入新 Qt 模块依赖

❌ A 的缺点

  • 3 个进程（pub长连接 + sub长连接 + 临时pub响应），进程管理复杂
  • 临时起 mosquitto_pub 发响应 → 每次都要重新 TLS 握手（~1-2秒延迟）
  • sub 进程 stdout 按行解析，JSON 可能跨行截断，需自己拼接
  • 命令响应不是实时的，"转发到LoRa然后等结果再响应"这种流程很难串起来

✅ B 的优点

  • 一个 MQTT 连接搞定全部：上报属性 + 收命令 + 发响应
  • 信号/槽驱动：收到命令 → 转发LoRa → 等结果 → publish响应，流程清晰
  • 内建 TLS、自动重连、QoS，不依赖外部 mosquitto 工具
  • 响应零延迟，不需要临时起进程

❌ B 的缺点

  • 需要安装 QtMqtt 模块（apt install libqt5mqtt5-dev 或自编译）
  • test.pro 加 QT += mqtt
  • 需要改造 IotUploader，把 mosquitto_pub 替换为 QMqttClient
  • 改动量比 A 大

🏆 推荐 B

虽然改动大，但 A 方案的"3个进程 + 临时TLS握手"在命令响应场景下根本不可靠。 华为云命令下发有超时限制（通常30秒），A方案光握手就1-2秒，加上LoRa转发延迟，很容易超时。 QtMqtt 一个连接解决所有问题，是正确做法。而且你的系统已经在 RK3588 上跑，装个 qt5-mqtt 包很简单。
